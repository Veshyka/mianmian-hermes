# 变更 2026-10-04：容器跑在 UTC —— 静默窗整体偏 8 小时（她凌晨 4-7 点连发 4 条）

**触发**：主人在凌晨收到她 4 条消息（「吃完火锅这会儿在干嘛呢 / 别是又躺下了 / 主人是不是睡过去了 /
那我把火锅那笔账记着，明天再找你算」），回我：「**晚上好像没暂停**」。

## 根因（实测证据）

1. **容器是 UTC**：`docker exec hermes date` → `Sun Oct 4 02:30:45 UTC 2026`；`TZ` 是空的。
2. 我写的静默窗用 `time.localtime()` 判点 → 容器把 **UTC 当本地** →
   「00:30–07:00 不触发」实际落在 **北京 08:30–15:00**，夜里完全不设防。
3. 日志对得上（容器 UTC → +8 才是北京）：

| 容器日志（UTC） | 北京时间 | p / 沉默 |
| --- | --- | --- |
| 10-03 20:33:55 | **10-04 04:34** | p=18% / 60 分钟 |
| 10-03 21:44:27 | **10-04 05:44** | p=21% / 70 分钟 |
| 10-03 22:04:58 | **10-04 06:05** | p=6% / 20 分钟 |
| 10-03 23:25:30 | **10-04 07:25** | p=24% / 80 分钟（这条已在窗外，正常） |

她的 4 条消息发送时间（`sent N segment(s) to <GROUP_ID>`）逐条对应上表 ✓。

## 改法

1. **新增 `plugins/onebot/onebot_time.py`**：全插件**唯一**的"给人看的时间"入口，
   固定 Asia/Shanghai（`ZoneInfo`，没有 tzdata 就退固定 +8，中国无夏令时等价）。
   提供 `now/at/hhmm/stamp/full_stamp/date/minutes_of_day/epoch`。
2. **改用它**的地方：
   * `proactive.py`：静默窗判断（`in_quiet`）、`awake_minutes`、跨日计数（`day`）、注入里的「现在 HH:MM」
   * `group_window.py`：她看到的每条群记录时间戳（**原来也是 UTC，差 8 小时** —— 顺带一起修了）
   * `adapter.py`：媒体目录日期、告警日志行时间戳
3. **清掉事故期间的统计**：旧状态文件（`ticks=6`、`day=2026-10-03`）是错口径攒的 → 移到
   `onebot-proactive.json.bak-before-tzfix-*`，重启后从北京「现在」重新计时。
4. 内部存储仍是 epoch，不动。

## 验证

* `check_proactive.py` 新增 `TestBeijingClock`（5 例）：
  * 先断言**这个环境真的是 UTC**（`time.localtime(北京 04:34) != 04`）—— 否则钉子没意义；
  * **事故钟点必须是静默窗**：北京 04:34 / 05:44 / 06:05 → `in_quiet=True`；
  * 边界按北京算：00:29 非、00:30 是、06:59 是、07:00 非、15:00 非；
  * 注入文本显示北京 05:30、跨日计数按北京；
  * 群窗口时间戳是北京钟点、且不含 UTC 钟点。
  * 原有用例的 `_ts()` 也从 `time.mktime`（UTC 时刻）改成 `_clock.epoch`（北京时刻）。
* 全量回归见末尾追加；已重启 `gateway-chat`。

## 教训（写进技能参考）

**容器里 `time.localtime()` 不是本地时间。** 凡是"给人看的时间"，一律走 `onebot_time`。
凡是"给人看的时刻"，先问一句"这是谁的表"。这次的形状和之前那些"静默失效"的坑一样：
**功能跑了、日志也有，但口径错了 —— 只有拿主人的真实感受去对日志才发现。**
