# 变更 2026-10-03：入库节拍改为**每两轮一次**（含退出冲缓冲）

**触发**：主人「能不能把群聊和私聊都改成每两轮入库一次，反正有切块在不会影响单块速度，
但是多一轮对话可能联系会更好一点」。

## 一、改了什么

`profiles/chat/hindsight/config.json`：

```json
"retain_every_n_turns": 2      // 原缺省 1（每轮都写）
```

* 作用域：**聊天门一个 profile**，群聊 + 私聊**同一条** provider 配置 → 两边一起生效。
* 干活门（本门，`/opt/data/hindsight/`）**没动**，仍是每轮写 —— 那边是本机运维记忆，越细越好。
* 备份：`profiles/chat/hindsight/config.json.bak-before-n2-20261003-183658`。

## 二、机制（bundled 自带，不是我们造的）

`sync_turn` 把每轮塞进 `_session_turns` 缓冲，`_turn_counter % retain_every_n_turns` 到 0 才
真正建 job 发出 —— 也就是说第 1 轮只在内存里等着，**第 2 轮到了才把两轮一起写**，
payload 里就是两轮的完整往返（实测 payload 同时含"第1轮"和"第2轮" ✓）。

* provider 是**每个网关会话一个实例**（bundled 注释与实测一致）→ 同一会话内缓冲能跨轮累积 ✓
* 会话切换（`/new`、压缩、`/resume` 等）→ bundled 自带 flush-on-switch，**缓冲不会丢** ✓

## 三、抓到的坑：退出时不冲缓冲，而且冲错了库

1. bundled 的 `shutdown()` **不冲缓冲**（会话切换才冲）→ 设 2 轮后，进程退出/重启会丢掉
   最后那 1 轮。→ 闸门里加了 `shutdown()`：缓冲非空就借 `on_session_switch(self._session_id)`
   复用它的 flush（先按旧 id 冲，再轮转；退出场景轮转无所谓）。缓冲空则不动。
2. **冲的时候不在群作用域里 → 那一轮群对话会漏进主库**（`mianmian-history`）。
   这是写测试时被抓出来的（断言"冲的时候必须还落在群库"直接失败）。
   修法：冲之前先从缓冲内容里抠群号（每轮 JSON 里带着标记），再包一层 `_group_bank_scope()`。

## 四、验证

* `tests/check_group_memory_redirect.py` 新增 `TestExitFlush`：
  1. 第 1 轮只进缓冲、不写库；`shutdown()` 后**必须**写出 1 条、且**bank = 群库**；
  2. 缓冲空时 `shutdown()` 不写任何东西。
* `tmp/probe_n2.py` 行为验证（截住出网那一步，不发真写入）：配置=2、provider 生效=2、
  第 1 轮缓冲（写 0 次）、第 2 轮写出且 payload 含两轮 ✓
* 全量回归见本文件末尾追加的实测数字。

## 五、代价（明说）

* 最后 1 轮要等下一次对话（或会话切换 / 进程退出）才入库 —— 换来的是"两轮成对，联系更完整"。
* 缓冲是纯内存：进程被 `kill -9` 硬杀仍会丢那 1 轮（正常退出/重启现在会冲）。
* 群里两轮共用一次 retain：标签取内容里的群号 ✓、`speaker:` 取两轮里最后出现的那个人。

## 六、2026-10-04 补：**干活门也改成两轮**（主人：「你自己这边也两轮一次，我直觉会好一点」）

* 改的是干活门自己的 `hindsight/config.json`：加 `"retain_every_n_turns": 2`
  （原先没有这个键 → 缺省 1 = 每轮都写）。备份 `hindsight/config.json.bak-before-n2-20261004-182117`。
* 用插件自己的加载器核实生效值：`retain_every_n_turns = 2 | bank = mianmian-history` ✓。
* ⚠️ 两边机制**不一样**：聊天门挂的是 `hindsight_guard`（里面有 `shutdown()` 冲缓冲补丁），
  干活门用的是 bundled provider **原样**，它的 `shutdown()` **不冲缓冲**（`plugins/memory/hindsight/__init__.py:1223`）。
  所以干活门这边：**正常换会话 / 压缩会冲**（flush-on-switch），被硬杀（容器重启）时最多丢当前那一轮。
* provider 是**每个网关会话一个实例** → 新配置对**下一个新会话**生效；本会话可能仍按 1 跑。
  想立刻生效要在容器里重启干活门网关（agent 不能重启自己所在的那个网关进程）。
