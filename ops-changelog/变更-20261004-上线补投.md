# 变更 2026-10-04：上线补投（不在线期间的消息，上线一瞬间补给她，最近 5 条）

## 主人原话
「他不在线，这段时间的所有消息，不管私聊还是群聊，都直接丢在队列里面吧，等他上线的一瞬间
全部丢进去，然后这个上线可以放低一点儿，就放最近5条…类似于"我才上线"…如果有点儿复杂的话，
直接复用群聊的那个原来的那个东西可不可以」

## 为什么必须由她这一侧做
- **私聊**：QQ 的离线消息确实要等账号上线才推 —— 但如果**她的网关**离线（NapCat 还连着），
  协议端往断掉的 WS 推的那些消息是**直接丢的**，不会有队列。
- **群聊**：QQ 客户端本来就**不补**离线期间的群消息 —— 窗口上就是个断档。
→ 所以「上线的一瞬间」得由她的适配器主动去历史 API 捞：`get_friend_msg_history` /
  `get_group_msg_history`（今天实测过，形状与事件一致）。

## 怎么做的（复用既有的两套，不造新轮子 —— 主人点名的方案）
| 场景 | 做法 |
|---|---|
| 私聊漏消息 | 合成**一个**回合（`_dispatch`，省掉 N-1 次 LLM），带「你刚上线」抬头，只给最近 5 条 |
| 群聊漏消息 | 直接追进**滚动窗口**（跟平时采集同一套）→ 她下次被叫醒时按 delta 看到；说明行写明「你刚上线：补上漏掉的 N 条」 |
| 群里的漏消息 @ 过她 | 补完**过一遍唤醒判定**（`_group_wake_trigger`）→ 一上线就把她叫起来回；平淡消息只进窗口不花钱 |

## 关键细节
- 抬头原文（她看到的第一行）：`[你刚上线 · source=qq-backfill]` + 「他给你发了消息：你不在线
  这阵子共 N 条，只给你最近 5 条（更早的没补，别当没发生过）：」
- **不重复补**：每条入站消息都会把该会话的游标往前推（`_mark_seen`），补投只取
  `time > 游标` 的消息；游标落盘 `onebot-backfill.json`，重启不丢。
- **补投的语音也转写**：历史消息走 `_history_text()`，record 段照样 `get_record` → whisper
  —— 否则补回来一堆 `[语音]` 空壳（刚修好的坑不许在新路上重犯）。
- 时序：协议端连上后等 `offline_backfill_delay_s`（默认 6 秒）再捞，给 NapCat 热身时间。
- 单会话失败只记日志，不影响别的会话，更不影响接收；历史 API 挂了就当没有。

## 开关
`offline_backfill_enabled`（默认 true）、`offline_backfill_max`（默认 5）、
`offline_backfill_delay_s`（默认 6）、`offline_backfill_state_path`（默认 `<home>/onebot-backfill.json`）。

## 上线后的实测（12:39-12:40，真环境）
1. `12:39:50` 重启她的网关 → `12:39:56` 日志：
   `[onebot] 上线补投完成：补了 0 条，无新消息的会话 1 个（共看 1 个会话）`
   —— 机制确实按「协议端连上后 6 秒」触发，认出 1 个会话（主人的私聊），并正确判定没有新消息
   （那条刚到的语音已经被正常收下了，游标挡住了重复补 → 不会把同一条消息既当新消息又当补投）。
2. **真实证据：QQ 确实会补推离线私聊** —— `12:38:59` 协议端连上 → `12:39:00` 一条他早前发的
   语音积压消息到货 → `语音转写成功（59948 字节 → 14 字）` → 她会话里看到
   `[语音: 我还等着你发呢 …]` → 正常回了他。
   也就是说：账号离线期间 QQ 会排队补推私聊（这层不用我们做），**群消息 QQ 不补**、
   **她的网关离线时协议端直接丢** —— 这两种才是补投真正要兜的洞。
3. 12:39:56 之前那次（12:38:58 启动）补投也跑了，只是旧日志只在「有补到东西」时才打一行，
   看起来像没跑 —— 已改成**无条件记账**（补了 N 条 / 无新会话 M 个），免得以后「静默=像没生效」。

## 上线后实测踩出来的四个坑（同一天全修完，每条都配了钉子）

1. **重复补投**（12:56 实测）：游标以前只在「补投结束」时落盘 → 那之后收到的消息虽然在内存里
   推进过游标，却没写盘；重启正好卡在这个缝里 → 12:56 把**她 12:51-12:53 早就回过的 5 条**
   又当「漏消息」补了一遍。
   修：`_mark_seen` 里节流落盘（`offline_backfill_save_every`，默认 15 秒），
   断开/停止时 `_flush_backfill_cursor()` 强制写。
2. **补投回合被她 `[SILENT]` → 主人手机弹 ⚠️**：Hermes 的规矩是「只有**机器回合**
   （自注入 `internal=True`，display kind `internal_notification`）才能在裸静默标记下整条不发；
   **人回合**装死 = 判「该回不回」→ 弹
   `⚠️ The model returned only a silence marker for a message that needed a reply.`
   （`gateway/run_turn.py:56`、`gateway/response_filters.py:_is_machinery_display_kind`）`。
   被重复补的那轮正是人回合 → 她判「这些我都回过了、没什么要说的」→ ⚠️ 到主人手机。
   修：`_dispatch(..., internal=True)`，补投回合算机器回合 → 她没话说就安静不发。
3. **补回来的媒体是空壳**：第一版只做语音转写 → 表情包补回来是光秃秃的 `[表情]`，没有本地路径，
   她看不见图。修：历史消息的正文改走**接收侧同一条链路**（`_text_with_media()` /
   `_group_text_with_media()`）→ 图片落盘、表情包顺手入库、语音转写全都有。
4. **群补投没下限**（双保险）：除了游标，再取「本群窗口里最新一条的时刻」当去重下限
   （`_window_last_ts`）—— 窗口本身是持久记录，它已经有的消息绝不再补一遍。

顺带（同批改动里的越界检查）：自动引用闸**只管引用段**，贴表情的锚点仍用 Hermes 原样传下来的
那个（`_emoji_anchor`）—— 不然关掉私聊引用会连带把「贴表情贴哪条」也改掉，属于越界。
