**触发**：主人「没有长期记忆，那我要的可以对不同群友有对应印象咋实现呢」→ 拍板「一个群库，加上群标签人标签，

## 一、拦路的一个坑：新库建不出来（已修，根因实测）

`PUT /v1/default/banks/mianmian-group` 连续失败：

```
could not resize shared memory segment "/PostgreSQL.xxxx" to 533794976 bytes: No space left on device
```

排查链（每步都有证据）：
1. `docker inspect hindsight` → **ShmSize = 67108864（64 MiB，Docker 默认）**，容器内 `/dev/shm` 也 64M。
2. 请求的 DSM 段 **533,794,976 B ≈ 509 MiB** ≈ 512 MiB → 而 `maintenance_work_mem` 当时正是 **512MB**
   → 建库要建向量表 + HNSW 索引，pgvector 的构建把 `maintenance_work_mem` 那么大一块放进共享内存。
3. 先把 `max_parallel_workers_per_gather/max_parallel_maintenance_workers` 置 0 → **没用**（还是同一个 509MB 请求），
   说明不是规划器并行度的事，就是 pgvector 自己那块 DSM。
4. 真正的修法（**DB 级、可逆、不重建容器**）：
   ```
   ALTER DATABASE "hindsight" SET maintenance_work_mem = '32MB';
   ALTER DATABASE "hindsight" SET work_mem = '16MB';
   ```
   ⚠️ `ALTER DATABASE SET` 只对**新连接**生效 → 还要让 API 的池重连（踢掉旧后端连接）才落地。
   落地后 bank 一次建成。
   回滚：`ALTER DATABASE "hindsight" RESET maintenance_work_mem; RESET work_mem;`（或改回 512MB）
   另注：`max_parallel_workers_per_gather=0 / max_parallel_maintenance_workers=0` 这次也留在库里了
   （当时的排除实验，无害；要还原同样 RESET）。
   备份：建库前主库未动；本改动**不碰任何数据**。

## 二、新库 `mianmian-group`（群聊人物印象库）

| `enable_auto_consolidation` | true | 跟主库一致，让噪音被整合成观察 |

## 三、闸门升级：`hindsight_guard` 加 `mode: block | redirect`

`/opt/data/profiles/chat/hindsight_guard/config.json` 现在：

```json
{"enabled": true, "mode": "redirect", "group_bank_id": "mianmian-group",
 "group_recall_budget": "mid", "group_recall_max_tokens": 512, "cross_group_recall": false,
 "blocked_chat_types": ["group","channel","supergroup","guild"], "marker": "source=qq-group"}
```

行为（redirect）：

* **写**：群回合的 `sync_turn` → **换 bank 到群库**再交给 bundled 实现（**用的是 Hermes 自己的 auto-retain，
  没有另起回填通路**，正是主人要的"直接用 hms 的机制"）。
* **标签**：`group:<群号>` + `speaker:<QQ号>`（机器人自己不算说话人）。
  ⚠️ 标签**不是**在 `sync_turn` 里挂的——retain 的 tags 是在 writer 线程跑 job 时才由 `_build_retain_kwargs` 拼的，
  那时上下文可能已切回私聊 → 所以改成**从内容本身算标签**（内容里带着群回合标记），无竞态。
* **读**：`_recall` / `_reflect` 换群库 + `tags=["group:<群号>"]`、`tags_match=any`（`cross_group_recall=true`
  时去掉群过滤 = 跨群认同一个人），并把 `recall_max_tokens` 压到 512。
* **工具**：群里 `hindsight_retain/recall/reflect` **仍然拦死**（分流只放行自动读写，防她手翻私聊库）。
* **私聊**：一动没动（bank 与召回全部还原）。
* `mode: block` = 老行为（群回合不写不读），一行切回；`enabled: false` = 完全退回 bundled。

`state.json` 现在带 `mode / group_bank_id / cross_group_recall / last_group_id`，计数新增
`retain_redirected / recall_redirected / group_turns`。

## 四、验证

**代码级（全绿）**：`tests/check_group_memory_redirect.py` 18 例 + 全量回归 **522 例 OK**（skipped=3）。
覆盖：纯函数抠群号/说话人；**机器人自己不算说话人**；群回合写群库 + 双标签；写完 bank 还原；
私聊仍写主库；`mode=block` 仍拦；`enabled=false` 完全透明；群召回查群库 + 按群过滤 + 512 token；
私聊召回无过滤；跨群开关；**会话键兜底**（正文没标记也认得出群）；群回合预取同步查群库；
群回合不排后台预取；block 模式预取仍拦；群里工具仍拦死、私聊放行。测试用假客户端截断网络出口，不依赖服务在线。

**真库侧（实测）**：
* 建库 `PUT` 成功 → `GET /v1/default/banks` 能看到 `mianmian-group`；`PATCH /config` 回读一致
  （`recall_max_tokens=512`、`enable_auto_consolidation=true`、两份 retain 指令都在）。
* 真闸门 + 真服务跑了一遍合成群回合（`tmp/verify_redirect.py`）：
  计数 `retain_redirected=1`、`last_group=9999999999` → 群库里**真出现了对应的 retain 操作**
  （`GET /mianmian-group/operations` 有 `retain` op）→ 说明**分流链路一路通到服务端**。
  这 4 条测试操作**已全部取消**（`DELETE /operations/{id}`），群库 stats 回到 0，没留测试数据。
* ⚠️ 事实落地（抽取出 nodes）**还没等到**：本机 llama-extract 只有 1 个槽，当时正被主库那批
  retain（主人正在群里聊，10 条 pending、有一条卡在 `retain_extract_facts` 250s+）占着。
  队列空出来之后，群消息的事实才会真正写进群库——这是环境已知瓶颈，不是分流的问题。

**踩到的四个坑（都修了 + 有测试钉住）**：
0. **真正的元凶：唤醒标记行里的群号被脱敏了**。`group_wake.TURN_MARKER` 原先把群号写成
   `mask_gid(gid)` → `<GROUP_ID>`，闸门正则抠不出数字。现场取证（重启后的 live 判别行）：
   `带标记=True 会话尾=bf0125 认出的群=-` —— 群回合**既没分流也没记数**（安静地失效，
   最坏的一种）。已改成**不脱敏**：这行只出现在她自己的回合正文里，她本来就知道自己在哪个群。
   并加漂移断言：`build_turn_text(...)` 必须能被 `group_id_from_text()` 抠出真群号。
1. **只认正文标记会静默漏**：Hermes 两条路径给 provider 的文本不一样（`sync_turn` 的
   `user_content` 可能不带回合正文），实测结果就是"群回合既没被分流、也没被记数"。
   → 改成**两路都认**：先认正文标记，再认**会话键** `…:group:<群号>`。标签同理，
   内容里没有标记时退用 lineage 标签里的 `session:` 值（跟着 job 走，无竞态）。
   （注：本机 provider 拿到的 `session_id` 是 `20261003_160832_45bf0125` 这种内部 id，
   不是网关会话键 `agent:main:onebot:group:<群号>`——所以兜底主要靠修好标记行。）
2. **预取会被计两次**：`prefetch` 与内层 `_recall` 各计一次 → 计数只在真正发起查询的 `_recall` 里加。


4. **`sync_turn(..., messages=[...])` 被基类拒收 → 静默不落库**（最阴的一个）。现场取证：agent 日志
   `WARNING agent.memory_manager: Memory provider 'hindsight' sync_turn failed:
   HindsightMemoryProvider.sync_turn() got an unexpected keyword argument 'messages'`。
   Hermes 只记一行 WARNING，闸门这边看着像"分支跑过了"（判别行都打了），实际 retain 根本没建。
   修法：新增 `_forward_kwargs()` —— **只把基类签名认识的参数转发给基类**，其余丢弃并记一行 INFO；
   `sync_turn` / `handle_tool_call` 两条转发路径都过它。复现命令见 `tmp/probe_retain.py`
   （带 `messages=` 时能把 TypeError 打出来，修完则打出"已丢弃 ['messages']" + retain 落到群库）。

**live 实测（重启后，群 <GROUP_ID3> 真消息）**：
