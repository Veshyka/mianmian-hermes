# 变更 2026-10-04：表情包自动打标（入库排队）+ 出站按情绪发图

## 主人原话
「入库自动就等着排队识别表情打标签吧，这个让本地就应该能做，这个模型能力应该是够的，
至于发的时候可以随机选，比如开心，就从几个里面随机一个就好了」

（这推翻了 2026-10-03「不做 VLM 自动打标」的决定 —— `sticker_lib.py` 里那段记录已同步改掉。）

## 怎么做的

**① 打标：入库只入队，后台 worker 慢慢消化**（`plugins/onebot/sticker_labeler.py`）
- 视觉模型 = 本机 8081 的 **Bonsai 27B + mmproj**（跟 `auxiliary.vision`、Hindsight 抽取同一个实例）。
- 它是 `--parallel 1`：当场同步打标会**卡住接收循环 + 跟记忆抽取抢唯一那个槽** →
  所以入库只 `note_new()` 入队，worker 每次打 `batch`（默认 3）条、每条之间歇 `interval_s`（默认 15s）。
- 启动时扫一遍库里「未标」的（她偷图时不在场那些）；已标的不重复排。
- 同一条最多试 `max_attempts`（默认 3）次，超了本次进程内放弃；打不出来留在「未标」。
- 顺手白捡：入库时协议端给的 `summary`（如「[笑]」）当线索一起写进标签，零成本。

**② 挑图：标签 + 随机**（`StickerLib.pick`，本来就有；这次把 `touch` 补上）
- 她说「开心」→ 在带该标签的几条里随机一条（带近义扩展：开心/高兴/笑/乐…）；
- 挑中会 `touch`，让她自己的 LRU 记住「这张用过」，别当最旧的淘汰。

**③ 出站：`[表情包:开心]`**（协议层 `extract_sticker_markers` + 适配器 `_sticker_cq`）
- `[表情包:开心]` 按情绪挑一张；`[表情包:/abs/x.gif]` 指定那张（她把入库正文里的路径抄回来也认）；
  `[表情包]` 随便一张；一条消息最多 3 张。
- 标记**先剥掉**（主人永远看不到），正文照发，图片段追加在这条消息末尾（分段之前）。
- 挑不到（库空/标签没匹配）→ 正文照发、只记账，**绝不因此让整条消息失败**。
- 发的是**普通图片段**（`[CQ:image]`）：QQ 会显示成图片而不是"真·表情包"——
  自定义图当表情包发需要 `mface`（商城表情包 id），本机没法给自偷的图申请，这是已知边界。

## 提示词：第一版会「偷懒」，改了问法（实测对照）

同一批 4 张真表情包，三种问法：

| 图 | ① 直接问 tag | ② 先描述再定标签 | ③ 给判据+先描述（**采用**） | 我自己视觉读完的参考 |
|---|---|---|---|---|
| 8977b52f40038825.gif | 累 | 无语 | **无语** | （未独立读） |
| 85e10f0e67b18cf5.gif（头顶问号） | 无语 | 疑惑 | **疑惑** | 问号 → 疑惑 ✓ |
| a7890c8a34c93d59.jpg（冷淡脸） | 开心 ✗ | 无语 | **无语** | 无语/冷漠 ✓ |
| d9f2704946bae1cf.jpg（托腮圆脸） | 开心 ✗ | 开心 | **害羞** | 我读是"无语/发呆"，③ 读"脸红捂脸→害羞"——**这张仍有分歧** |

结论：**直接问 tag 会偷懒**（两张不同图都给「开心」）；**先描述再定标签 + 给判据**好得多（4 张里 3 张与我的独立读法一致）。
所以生产用 ③ 的提示词。⚠️ 但**别把模型标签当事实**：出错时她自己可以 `[表情包:/路径]` 指定，
或者用 `sticker_lib.py tag --hash … --tags …` 手写覆盖（比模型准——她偷图时在场）。

## 上线后自查抓到的两个真 bug（都不是新功能本身，但是新功能牵出来的）

**① 打标调用会卡死她的网关（严重）**：`_ask()` 里 post 回调写得对，但**调用方式是同步的**——
`urllib` 阻塞调用直接在事件循环里跑，超时给到 600s → 一次打标能把接收循环和所有回合卡几分钟。
修：`await asyncio.to_thread(post, …)`（协程回调仍直接 await）。测试补了一条「模型调用不许堵事件循环」
（并发 ticker 数节拍，堵住就 <5 下）。这类"回调写成 async 但调用是 sync"的坑，写插件时是默认陷阱。

**② 群被当成私聊，记进了主动起头名单**：群「<GROUP_NAME>」<GROUP_ID2> 出现在 `onebot-proactive.json`
的 `chats` 里 → 她 15:00 朝它发「主动私聊」→ 协议端 `retcode=1200 无法获取用户信息`（不是好友）
→ 连发失败 + 一条自检告警（主人私聊里会看到）。
根因：`group_ids` 只在**收到该群的消息时**才 add（`_register_inbound`），学晚了就按私聊处理；
而 `_is_group_chat()` 只看这个集合。
修：连上后向协议端要一次 `get_group_list`（权威，3 段退避），灌进 `group_ids`；
顺手把主动起头名单里出现的群号清掉（`_load_group_ids`）。实测重启日志：
`群号名单 3 个（新学 3 个：<GROUP_ID>, <GROUP_ID>, <GROUP_ID>）` + `主动私聊名单里的群号 <GROUP_ID> 已清掉`，
状态文件只剩 `['<OWNER_QQ>']`。

## 上线补投的三个补丁（同批，重启后实测发现）
1. **假会话拖垮补投**：重启后 `get_friend_msg_history` 连续失败，日志带上协议端响应才看清——
   `retcode=1200 记录10001不存在` / `消息undefined不存在`。**10001 和群 55555/66666 是单测的假 id**
   （e2e 夹具写进了真 profile 的 `onebot-backfill.json`：`dm:10001`、`group:55555/55556/55557/66666`）。
   已清游标（只留 `dm:<OWNER_QQ>`，备份 `onebot-backfill.json.bak-before-clean`），
   并在夹具里把 `HERMES_HOME` 指到临时目录 + 收尾还原 → 以后单测再也写不进真 profile（跑完 640 例复查游标=干净）。
2. **永久性失败不再空转**：协议端说「…不存在」时立即跳过（不是热身问题），别重试 5 次白拖 30 秒。
3. **重试阶梯 3 次 → 5 次指数退避（3/6/12/20s）**：重启那阵 NapCat 热身比 9 秒长。
   实测重启后：`补投完成：补了 0 条，无新消息的会话 1 个（共看 1 个会话）` ✓。
   （对照：协议端 HTTP 直连 `get_group_msg_history`/`get_friend_msg_history` 用 `group_id/user_id + count`
   就正常返回 messages，说明**不是参数问题**，就是假 id 问题。）
