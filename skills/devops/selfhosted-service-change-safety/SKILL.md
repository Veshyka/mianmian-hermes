# 自建容器服务「换后端 / 调参」安全规程

适用范围：本机自建容器服务（记忆库 Hindsight、推理 llama.cpp/Ollama、代理、媒体库等）要**换模型、换后端、改向量维度、调关键参数**时。核心：任何改动都要**能量、能回滚，且不会在下次重建时静默丢失**。

## 铁律

1. **调优值必须落在「会被重跑的那份产物」里——而且先确认哪一份才是真在生效的那份。**
   只存在于一次手工 `docker run` 命令行里的参数，下次重建容器就没了——而且**不报错**，只是悄悄退回默认值，看起来像「本来就该长这样」。
   本机现状（已核对）：**compose 管的服务，落点是 `<映射目录>/stack/<服务>/docker-compose.yml`**，改完 `docker compose up -d` 重建即生效。**别再往 `<映射目录>/scripts/<服务>_switch_*.sh` 这类 docker-run 脚本里写**——那是 compose 化之前的老路径，多半已下线或已过期，照它重跑反而会静默丢掉全部调优（本机 `hindsight_switch_llamacpp.sh` 就是这种残留）。
   **动手前先确认目标服务现在归谁管**：
   ```bash
   docker inspect <容器> --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'
   ```
   非空 → compose 管，**输出里那份文件才是唯一真身**；为空 → 才是手工 `docker run`，这时才需要维护重建脚本。
   值旁边写一行「为什么是这个值」，并带上「怎么量出来的、量尺在哪」。

2. **先建量尺，再动参数。**
   没有可复现的评测就别调参——否则分不清「变好了」和「运气好」。量尺四要素：真实历史问题（不是自己编的）、客观判分、结果落盘、支持前后对比。**禁止靠感觉或抽样个案下结论。**
   **量尺本身要先验分辨率，再信小差异**：①被测服务重复同一请求的返回是否逐位一致（不一致时 ±1 名 / ±0.01 分整个是噪声）；②每题的正类数（期望关键词实际命中的条数）是否落在有意义的区间——正类 ~1 条或占比 ~70% 的题等于没量；③样本量撑不撑得起结论——配对 bootstrap 的 95% CI 跨 0 只能说「测不出差别」，不能写成「新的略好」。具体做法见 `references/hindsight-embedding-migration.md`。

3. **一次只动一个变量，扫出拐点再定值。**
   候选值连续扫（如 0/2/4/6/8），取「精度不掉、代价最小」那一档；拐点两侧都要有数据，才能判断是过狠还是不够。**别信直觉**——实测常有反直觉项（把量级档位调低反而掉精度）。
   - **扫的时候要把上限一起扫进去**：参数空间不一定是单调的，**最高那档可能整类失败**。实测：按模型卡推荐把采样温度调到顶档后，模型不再输出约定的外壳对象、改写裸数组，调用方按 schema 反序列化时**整条被拒 → 那批数据不是变差而是直接丢失**，比中间档糟得多。只扫「够用」的低区间就会漏掉这道悬崖。
   - **指标要分层看，别只报一个总通过率**：单一「合规率」会把字段级脏数据盖住（实测某档外壳结构 6/6 全过、字段层却有 3/6 带空必填字段）。至少报三层：外壳/结构合规 → 字段级零瑕疵 → 产出质量（如因果边数）；另加**防刷量检查**——数量涨了要验证不是把同一项拆碎、或全挂到同一个锚点上凑出来的。

4. **改后端/模型/维度：起平行实例，先量后切。**
   绝不在生产实例上直接试。平行实例 = 另一端口 + 独立 volume + 不自启（`--restart no`，别让它长期吃内存）。用官方导出/导入把真实数据搬过去，与生产对打，赢了才迁。

5. **切生产是唯一有停机的一步，前置条件齐了才做：**
   最新备份 + 一键回滚 + 回滚命令写在与切换同一个脚本里（支持 `rollback` 子命令）+ 已量出「新配置更好」的证据。

6. **认领「之前已做过」前先核实际状态。**
   笔记/技能里写着「已配好」不等于现在还在——配置会静默丢失、记忆会过期。用户说「之前让你做过 X」时，**先查实际状态（配置/env/文件/数据）再答**，别凭记忆认领，也别辩解；查完发现确实没落地就直接认 + 补上。同理，自己声称「已改好」前要有一条读回来的证据（读回 config、看到 env、看到文件）。

7. **先证明「这个键 / 这个特性在本机存在」，再讨论它的值。**
   外部（别的模型、网上帖子、方案清单）给的参数名和默认值经常整条不存在——照抄的后果是**静默无效**：不认识的键 PATCH 不报错，写进 config 的键插件根本不读，看起来「改过了」实际什么都没变。三处权威源逐一对上才认：
   ① **客户端 schema 源码** = 键名与默认值的唯一权威（本机范例：`/opt/hermes/plugins/memory/hindsight/__init__.py` 的 `get_config_schema()`，人读版在同目录 `README.md`）——用 search_files 搜键名，别凭记忆；
   ② **服务端能力**：`GET /version` + `curl .../openapi.json`，在 `components.schemas` 里查字段与枚举（static/env 级字段不在 openapi 里）；
   ③ **现场生效值**：调用方各自的 config 文件——同一服务可能有多个调用方（各 profile 一份），逐个读，别只看默认那份。
   同一把尺子也用来验「特性是不是已经有了」：讨论「加增量/增强 X」之前先读客户端源码里那条调用路径——实测增量 retain 早已默认在跑（API ≥0.5.0 走 `update_mode='append'` + 水位线，只发新轮次），差点被当成待办再实现一遍。
   核对完把「真存在的键 + 默认值 + 现场值」抄进技能，下次不必重查。

## 规程

1. 写清现状与目标（当前后端/维度/参数 → 想换成什么）
2. 找到衡量它的量尺；没有就现造一个（铁律 2）
3. 量基线并落盘（带 tag）
4. 平行实例上改**一个**变量 → 复量 → 对比
5. 定值 → 写进规范重建脚本（含理由注释）→ 生产执行 → 复量确认
6. 记录写进脚本注释（值 + 依据 + 踩过的坑），别只留在对话里

## 改「配置文件驱动」的服务（settings.yml / config.yaml 型）

配置文件驱动的服务（SearXNG、mihomo 等）改参不用重建容器，但要按这个顺序，每步都能回滚：

1. **先定位配置的「真身」**——容器内路径往往只是挂载点：
   ```bash
   docker inspect <容器> --format '{{range .Mounts}}{{if eq .Destination "<容器内配置路径>"}}{{.Source}}{{end}}{{end}}'
   ```
2. **备份真身**（`cp <Source> <Source>.bak-<时间戳>`），并记下原属主/权限（`stat -c '%U:%G %a' <Source>`）
3. **先校验临时副本**：新文件拷到容器 `/tmp`，在容器内跑解析/YAML 校验，**别先覆盖生产**
4. **写挂载源**（不是容器内路径），写完 `chown`/`chmod` 还原第 2 步记下的属主与权限。**别借机改既有目录的属主**——需要新目录就新建一个自己拥有的子目录（宿主权限细节见 `hermes-container-ops` 技能）
5. **重启 + 健康检查**：轮询 N 次，判据是「真能出结果」，不是「进程起来了」
6. **健康检查失败就自动回滚**（拷回备份 → 重启 → 再验），并把回滚命令打印到输出里，方便人工兜底

把 1–6 写成一个**幂等脚本**（可重复跑、每次先备份），而不是每次手工敲命令——本机范例：`/opt/data/hindsight-eval/searxng_fix/apply_settings.sh`。

## 退役 / 下线：删一个服务、一段配置或一批文件

小到「删掉一段注释」也按这个走。核心：**先证明没人用 → 再证明只删了该删的 → 留退路 → 登记**。

1. **先证明没有活引用**。删之前把**活配置**（compose、调用方 config、脚本）搜一遍，确认没有生效项还指向它。
   典型误判：把「用户说不用了」当成「已经没人引用」。要分开核三件事——服务容器还在不在、调用方的 config 指向哪个端点、有没有脚本还引用它。**没引用才动手**；有引用就先改引用方。
2. **备份，并把回退指针写在改动旁边**：`cp -a <文件> <文件>.bak-before-<动作>-<时间戳>`，然后在原地留下的注释里写上这个备份名——只写在对话里的回退指针等于没写。
3. **改完必须证明「只删了注释」——不能靠眼看**：**剥掉注释与空行后逐行 diff**，行数一致才算生效配置零改动 → `scripts/verify_config_comment_only.py <旧> <新>`。
   为什么必须做：注释掉的服务/参数与生效内容长得几乎一样，肉眼扫不出来；而「以为只动了注释、其实连带删掉一个生效参数」这类错**不会当场报错**，要到下次重建才炸。这也是「改注释不用重建容器」这个结论的证据。
4. **删一段注释块前，先把块的真正结尾读到**。按印象截断 `old_string` 会留下**孤儿行**（实测漏了块的最后一两行，得再补一刀才干净）。判据：块从开头注释行起，一直到下一个非注释键或 EOF，中间每一行都要包进去；删完往回读 15 行复核。
5. **删文件走回收站，不用 `rm`**：`trash-put`（本机装在 `~/.local/bin/`，**不在 PATH 里，要用绝对路径**），7 天内 `trash-restore` 可捞，删完用 `trash-list` 复核。**回退模型/备份文件不顺手删**——那是唯一的退路，除非用户明确说不用了；删之前先确认「删了还能不能回去」。
6. **只改注释不用重启**（生效配置没变），但**服务健康要复验**：改完挨个打一遍健康端点确认 200，别拿「我没重启所以肯定没事」当结论。
7. **登记到两个台账**：`ops-changelog/README.md`（变更摘要）与 `ops-changelog/ownership-changes.md`（删了哪些文件、为什么、怎么回滚、怎么验证）。**删文件尤其要登记**，否则下次没人知道东西去哪了。

## 改「服务级 env」类参数（只能重建容器才生效）

服务级 env（`HINDSIGHT_API_*`、模型/端口/并发这类）不重建不生效，而每次重建都是一次真停机。按这个顺序走：

1. **一次只加一个变量，加完就重建 + 验，验过再上下一个。** 一批塞进去，一旦起不来就不知道是谁的锅（实测：三项 env 单独加稳定，四项一起加后服务在启动数分钟内崩溃重启）。
2. **存活判据 ＝ 真打一次业务请求，不是「容器 Started」**：
   - 从**消费侧容器**里打 API（`python3 -c` + `urllib.request`；宿主上常常没有 `curl`）。容器访问 `172.17.0.1` 必须显式绕过代理（`NO_PROXY=127.0.0.1,localhost,172.17.0.1`，curl 用 `--noproxy '*'`）。
   - ⚠️ **别用 `ss -tln | grep <端口>` 判监听**：`grep 8888` 会命中同机的 `18888`，得出「在监听」的**假结论**。要 grep 就锚定 `:<端口>\s`，更省事的是直接打 API。
   - **「起来了」还要再看几分钟**：崩溃重启循环往往在启动后几分钟才发生。跑过一轮真实业务之后，核对 `docker inspect <容器> --format 'RestartCount={{.RestartCount}}'` 仍为 0、`ExitCode=0`、`OOMKilled=false`。
3. **起不来就回滚到已知可用状态，再逐个重放**：`cp docker-compose.yml.bak-before-<动作>-<ts> docker-compose.yml && docker compose up -d`（备份放同目录；目录属 root 时走「容器侧写暂存 + 宿主 `sudo -A cp` 覆盖」）。
4. **拿不准的单个变量，先起一次性探针容器，别在生产上试**：同镜像 + 临时数据目录 + 空闲端口 + `--restart no` + 名字前缀（如 `hs-probe-`），观察若干分钟看是否崩。**任何 `rm` / `docker rm` 前先回显确认目标名带前缀**，别误伤生产容器与数据卷；用完拆除并把临时目录列进清理清单。
5. **一项一验一报**：把「改 → 重建 → 验 → 报」拆成独立小步，别在一轮里堆「改多个文件 + 重建 + 验证 + 写报告」。单轮动作过大时整条操作会被运行时丢弃（表现为「什么都没改」），你以为做了、其实一步没落。每步都要能在中途停下而不留半成品。
6. **验证分三层，缺一层都不算验完**：①**回读**——新值真进了运行中的进程（读回 config，或容器内 `env` 里看到）；②**行为**——找一条**值能证伪**的日志说明这个特性真在干活；③**稳定**——过几分钟再看 `RestartCount`/`ExitCode`/`OOMKilled` 仍正常。
   - 「行为」这层最容易漏：**光看日志里有这行不算，要看那行里的数字**。实测同一个重排特性，未生效时日志是 `RRF merge … in 0.000s`（直通、没算分），生效后才是 `… candidates scored in 0.961s`——**时间非 0 才证明它真在算**。开任何「后台异步」特性前，先想清「它没干活时长什么样」，再拿那个特征去比对。
   - 拿不到行为证据就别报「已生效」，报「已回读、行为未证实」。

## 已知会咬人的点
- **配置文件可能是 bind mount**：往容器内配置路径 `docker cp` 覆盖会报 `device or resource busy`（那是挂载点，不是可写层的文件）。踩过一次：命令报错被忽略、重启后配置没变，症状看起来像「改了没用」。**改的一定是挂载源**（上面第 1 步查出来的）。
- **运维脚本必须按成功数统计、以退出码反映失败**：把「尝试数」当「成功数」会报假成功——挂到 cron 上就是长期静默失败，而人还以为清理/备份在跑。自写脚本三条：只统计真正成功的条目；有失败非零退出；无事可做时输出为空（静默 = 不打扰主人）。排查时**先看退出码**，别只看最后一行汇总。
- **CLI 不在容器 PATH 里**：不少镜像把管理命令装在 `/app/.../.venv/bin/` 之类，`docker exec <c> <cli>` 报 not found → 用绝对路径。查到路径后写进技能，别每次重找。
- **配置分「可热改」与「只能重建」两类**：动手前先确认目标字段属于哪种。可热改的（服务/bank 级 config 接口）PATCH 即生效、免停机；服务级 static 字段通常只能靠重建容器带 env。**先试一次 PATCH 拿报错**——报错往往直接列出哪些字段可改，比翻源码快。
- **假健康告警**：healthcheck 写死端口、与实际监听端口不一致时会长期标 unhealthy，别据此判断服务坏了。
- **改 root 属主目录下的文件：原子写工具会 `Permission denied`，即使文件本身归你。** `patch`/`write_file` 走的是「同目录建临时文件再 rename」，目录不可写就整体失败（本机 `stack/<服务>/` 是 root:root 755，属此列）。做法：**在可写目录生成并校验新内容 → 再覆盖真身**：容器侧写到 `/opt/data/tmp/`，宿主侧 `sudo -A cp` 覆盖（SSH + `SUDO_ASKPASS=/vol1/1000/<USER>`）。**语法校验用服务自己的解析器**（如 `docker compose config -q`），别依赖本机 YAML 库——容器里未必有 `pyyaml`。改完 `grep`/`diff` 回看，确认只动了预期那一行。
- **重建后的一次崩溃，先读栈再怀疑自己刚改的 env**：带内嵌数据库（或固定端口依赖）的服务，重建时新实例可能在依赖就绪前就启动 → `Application startup failed. Exiting.` 报一次 → 被 restart policy 拉起后一切正常。实测那次的真因是 `connection to 127.0.0.1:5433 failed: Connection refused`（内嵌 PG 还没起），**与刚加的离线旗标无关**；只看「改完就崩了」会误判成参数有问题并白回滚一次。判据：`RestartCount=1` 且 `StartedAt` 就在容器创建后几秒 + 之后长期稳定、日志有后续的成功启动行 = 重建竞态；`RestartCount≥2` 或持续重启才是真崩。**下结论前把那一段栈抓出来读**。
- **本地已缓存的模型/权重仍可能在启动时联网**：构造阶段去列远端仓库（`list_repo_tree` 这类）会撞域名黑洞 → 启动失败退出；**调大 init 超时无效**（那是硬连接超时，不是加载慢）。修法：给服务加离线旗标（HF 系 `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1`）让它只用本地缓存。**镜像里有缓存 ≠ 不会联网**。
- **别把生效脚本的门槛写成猜测的数字**：`assert <grep 出来的计数> == N` 这类自检一旦猜错，`&&` 链会**静默停在自检**、后面的应用步骤（`docker compose up -d`）根本不执行——而前一步的文件已经落盘，看起来「改过了」。做法：先打印实际值、确认，再让动作步骤**独立执行**；自检失败要显式退出并回显「期望 vs 实际」，别让它变成静默的门。
- **重建后不通的排查顺序**：容器起没起 → 端口监听 → 依赖后端（LLM/embedding 端点）通不通 → 数据卷挂对没。
- **数据在 volume 里，重建不丢**：先确认哪部分是 volume 里的持久数据、哪部分在容器可写层，再决定「重建」还是「必须迁移」。

- **「工具层做不到」要先读工具 schema 再说**：Agent 侧能做的事上限 = 工具定义里声明的入参。要写「让 Agent 自己按条件动态过滤/收窄」这类方案前，先读工具定义（本机 memory 工具：`recall`/`reflect` 只收 `query`，`retain` 收 `content/context/tags/occurred_at`）——超出入参面的需求只能改插件或裸调服务 API，写成「让 Agent 自己决定」是空头方案。
