# 告警通道设计规则（本机血泪版）

> 来自 2026-09-23：换聊天通道那天，**告警没响**——因为它挂在被切走的那一方。

## 一、告警通道不能依赖被退役/被切换的组件

**事实**：当时的告警路径是「体检脚本 → `POST 127.0.0.1:8098/report` → 旧框架(AstrBot)插件 → 转发到主人」。平台一搬走，旧框架收不到消息，它自己的平台类发送必然失败 —— 实测那条投资返回 **HTTP 500**，告警静默丢。

**规则**：告警/看门狗必须挂在**当前底座自己的官方机制**上，旧侧端口最多当副保险，不能当主通道。

本机现行主通道（已验证）：Hermes 官方 cron 的 `--no-agent` script-only 模式：

```bash
hermes cron create "*/30 * * * *" --name <名字> --no-agent --script <包装脚本.py> --deliver <目标>
```

- 脚本 stdout **原样投递**；空 stdout = 静默 tick（不打扰）。
- 包装脚本只**调用**体检脚本，不改它的检查逻辑；自身恒 exit 0（真实故障走 stdout，非零退出留给「包装器自己坏掉」的兜底）。
- 每条运行都追一行台账（时间 + rc + 结论），异常时另写明细文件。

## 二、分级：能自愈的不出声

- 健康 → 空输出 → 不投递；
- 恢复 → 只写日志；
- **同一异常签名**（异常项名集合，**不含会变的读数**）持续时，第 N 轮才二次提醒（本机 8 轮≈4h）；异常变化 → 立即提醒。
- 全都告警 = 没有告警（告警疲劳）。

## 三、验证告警必须「故意失败一次」

判据不是脚本退出码，而是**它真的到达了人**：投递台账里有 `delivered to <目标>` + 主人那头真收到（最好让他引回一条）。本机做法：脚本里留一个演练开关（`touch <flag>` → 下一轮强制走告警分支、标注【演练】），**验完立刻删**，并在报告里说明该文件当前不存在。

## 四、体检项要包含「参数漂移」

只看进程活着不够。必须检：防抖窗口、白名单项数、补丁在位、常驻开关等**容易被别处改回旧值**的参数。**示例：切换后旧底座的「平台未连接/平台类 ERROR」会持续存在，必须按「退役待命」降档**，否则毎 30 分钟误报一次。

## 五、日志纪律

状态心跳只写**计数、时间戳、错误摘要**，绝不含消息正文、附件路径与凭据。

## 六、自检/体检脚本本身的可靠性

- **用带依赖的解释器跑**：本机 `doctor.py` 必须 `/opt/hermes/.venv/bin/python`——系统 `python3` 缺 `yaml` 会把配置项误判成「未启用」。
- 体检脚本带 `--json`（机器可读）与 `--no-alert`（只打不告）两个开关，方便包装器与人工复用。
- 体检项清单：双侧门 / A2A / 记忆库 / 插件在位 / 补丁在位 / 参数漂移 / 监听端口 / 心跳文件新鲜度。

## 七、「每条都发」= 刷屏；去重闸门要落在**发送前**

真实事故（2026-09-23）：健康自检的回执每两分钟刷一次同样的失败。判据没错，错在**每条都发**——任何被循环/被反复调用的检查脚本，只要没有去重，就会被调用方放大成刷屏。

**落地法（本机 `scripts/health_all.py`）**：签名 = 当前异常项 id 的集合（**不含会变的读数**，否则每轮读数一变就算「新异常」）；同一签名在冷却期内（默认 4h）只发一次，**恢复（overall=ok）即清零状态文件**，演练开关不受冷却限制。静默轮仍然打印总览与明细（标注「已去重、本轮不打扰」），只是不投递——不然「没告警」和「没跑到」分不清。

**自检的判据**：`scripts/check_health_dedup.py`（离线、把探针与发送通道换成桩，直接跑真实 `main()`）：首报 1 条 → 重复 3 轮静默 → 签名变立刻再报 → 恢复清零 → 恢复后再报 → 过冷却再提醒；`scripts/check_health_cron_dedup.py` 同理验证 cron 包装器（10 轮只投递 2 次，每轮仍落日志）。**改了去重逻辑就跑这两个脚本**，别只在脑子里推。

## 八、告警回路会自我放大：别让告警通道本身出现在被检指标里

真实事故（2026-09-23，`ab-errors` 反复误报的机制）：体检脚本把回执 POST 给旧框架的 `:8098/report` → 旧框架要把回执推给主人，但它的平台已被切走 → 发送失败**又写一条 ERROR** → 下一轮体检把这些 ERROR 计入 `err_count` → 继续判失败、继续回执……闭环自激，看起来就是「每两分钟刷一次同样的失败」。

**规则**：① 告警出口不能同时是被检对象的错误来源（旧框架退役后，一切「经旧框架发消息」的路径都要整条删掉，不是关掉）；② 排查「同一条失败反复刷」时，先画一遍「谁产生错误 → 谁统计错误 → 谁触发告警」的环，环上有同一条链路就是自激。

## 九、判据要对「刚启动」留宽限期，否则每次重启都误报

真实事故（2026-09-23，QQ 小号线「NapCat 协议端从未连上」）：网关 07:37:59 重启、NapCat 07:38:48 因改配置重启，**中间 ~35 秒协议端还没连上**，而判据只看「有没有连过」不看「本进程活了多久」→ 直接判 fail 并告警；07:39:04 协议端连上、自愈。

**规则**：凡是「对端会自己重连」的自检项（反向 WS 客户端、上游连接、订阅），判据必须带**进程启动宽限期**（本机 `client_grace_seconds=180`）：宽限期内「从未连上」降为提醒、「启动至今没收到事件」直接静默，**超出宽限才 fail**（保证不是放水）。状态文件里要有 `started_ts` 作为基准；**缺失时退回原严格判据**（老状态文件/合成状态不能被静默放松）。回归用例要同时钉住两条：宽限内 → 不 fail；宽限外 → 仍 fail。

## 十、旧组件退役后：判据要按「显式推出的预期状态」分层，且别拿启动时的旧日志当现状

真实事故（2026-09-23，AstrBot 退役后仍被自检报故障 + 报 warn 噪音）。三条规则：

1. **预期状态要从外部配置显式推出来**，别用阈值凑：本机读 NapCat 的 `websocketClients[].url`——指向新底座 `:6700` 即「旧门已退役」（它的适配器不可用、平台类 ERROR 都是**必然**的）；回指旧端口 `:6199` 即「在役」，此时适配器掉线才算故障。**同一份判据在两种状态下含义不同**，所以状态本身也要作为一条检查项打出来（可读、可复核）。
2. **进程/容器停着也可能是预期**：退役状态下容器 `state=exited` 就该是 **ok 并跳过**运行态类检查（插件参数/工具面/补丁/适配器/ERROR），不是降级成 warn——warn 一样会推给人，等于没降噪。容器重新起来（探测到 `running`）这些检查要**自动恢复**，别把跳过写死。反过来「在役却停着」必须 fail。
3. **日志判错误：按时间戳切「事件」+ 分级，别用 `grep -A N`**：一次嵌套 traceback 里有多个 `Traceback (most recent call last)`，按行切会切碎、块内窗口看不到关键字 → 把**同一个**故障误判成若干「非平台类错误」。正解：一个事件 = 一条带时间戳的日志行 + 其后所有续行（traceback 正文），事件内**任意一行**命中关键字即整件事归该类（本机 `scripts/ab_log_classify.py`，宿主侧 reading `docker logs` 的 stdin）。
   - **ANSI 转义要先剥**：容器日志带 `\x1b[..m` 颜色码，`^\[` 这类锚点会全部失配（实测踩到）。
   - **故障级别要分开**：`[ERRO]` 级才判失败；只有 traceback 的 `[WARN]` 级（工具/agent 单次调用出错）只记不报。
   - **「XX 已连接/正常」是启动时刻的旧行**：进程后来掉线，那行仍留在日志里 → 判「现在连没连」要找**之后的硬证据**（如 `ApiNotAvailable`、`Failed to send`），否则退役后会一直误判成「还连着」。
4. **分级要落到「发送前」**：体检脚本的 ⚠️（提醒）与 ❌（失败）必须在**投递层**区分——只有 ❌ 才投递，仅 ⚠️ 只写日志（本机 `scripts/health_cron.py`；离线回归 `scripts/health_cron_grade_selftest.py` 覆盖「全绿静默 / 仅⚠️静默 / ❌投递 / 包装器自己崩了仍投递」四种）。改分级就要重跑这个脚本。

## 十一、主通道落地：magicpush（本机 `:818`）

magicpush 是应用商场托管的推送服务（容器名 `magicpush`，容器内 3000，宿主发布 **`0.0.0.0:818`**）—— 体检/看门狗脚本的告警主通道走它，**失败才回落** `hermes send`（回落链路也要真跑过一次，不能只写在代码里）。

```
POST http://172.17.0.1:818/api/push/<TOKEN>        # 宿主侧地址是 127.0.0.1:818
Content-Type: application/json
{"title": "...", "content": "...", "type": "markdown"}   # type: text|markdown|html
# 也支持 POST /api/push/ + Authorization: Bearer <TOKEN>
# 返回 {total, successCount, failedCount, results[{channelType, channelName, logId}]}
```

- ⚠️ **容器里必须显式绕过代理**：`NO_PROXY=127.0.0.1,localhost,172.17.0.1`（curl 用 `--noproxy '*'`），否则请求被容器代理接走。
- ⚠️ **token 是「接口级」的，接口必须绑了渠道才能推**：本机 `endpoints` 表里三条记录都有 token，但只有**绑了渠道的那条**能用；用错接口得到 `400 {"message":"该接口未绑定任何渠道"}`。选法：按名字取已绑渠道的那条（本机 `通用推送`），或查 `push_logs` 里最近有成功记录的 `endpoint_id`。
- **凭据保管**：token 只存 **0700 文件**（本机 `<映射>/secrets/magicpush.token`，权限对齐容器读得到的 askpass 脚本），脚本运行时读文件，**不写进脚本/技能/对话、不打印**；在宿主上从 SQLite 取 token 时先 `cp` 副本到 `/tmp` 再读，**读完 `sudo rm` 掉副本**（普通账号删不掉 root 建的副本）。
- **先单测通道再接线**：直接用 token 打一条 `POST` 看 200/`successCount=1`，再改体检脚本；改完用脚本自带的演练开关（`--simulate-fail`）跑端到端，**判据是告警行里写明走了哪条通道**（本机形如 `主通道=magicpush（magicpush HTTP 200 -> …）`），不是脚本退出码。
- 「到底发出去了没有」查 magicpush 自己的 `push_logs`（含 `endpoint_id`/`channel_type`/`logId`），别猜。

## 十四、给某个**组件**接告警：先查它自己的默认出口

体检脚本的通道对了，不代表每个适配器/插件自己的告警也对了——它们各自带着一个默认 URL，默认值往往就是那个早已退役的端口。

1. **接告警前先把该组件的默认出口 grep 一遍**：`grep -rn "report_url\|8098" <插件目录>`。本机踩过：适配器里 `alert_report_url` 默认 `http://172.17.0.1:8098/report`（已退役，实测 `000`），于是它的运行告警**每次都只写本地日志 + 一行 `alert delivery failed`**，没人知道告警通道其实是死的。
2. **请求形状由配置驱动、构成抽成纯函数**：magicpush 与本机旧 `hermes_report` 的体/鉴权方式不同（`{title,content,type}` vs `{task_id,status,title,summary,source}`；token 在 URL 路径 vs 走 `X-Report-Token` 头）→ 用一个 `_build_alert_request(base, token, *, magicpush, …) -> (url, headers, body)` 风格的纯函数分派，**保留旧形状当回滚开关**（一个布尔键切回去），不要把两种形状写在同一段拼接里。
3. **凭据不落配置文件**：配置只写 URL 前缀（写到 `/api/push` 为止，token 由代码从 0700 secrets 文件读并拼上）。写进 profile 的 `config.yaml` 就是把口令存成了配置项。
4. **形状要端到端测，不是只测函数**：用 `aiohttp.web` 起一个只收不回的假接收端（监听 `127.0.0.1:0` 拿随机端口），真调告警方法，断言它收到的**路径**（token 在不在 URL 里）、体字段与截断。只测纯函数会漏掉「URL 前缀抄错 `/api/push` 两遍」这类拼接错误（本机就是这么错一次被单测抓到的）。
5. **吞噪声的那类闸门要放在「算不算她说话」之前**：被吞掉的告警/提示不算「她开口了」，**别让它把主动起头的斜坡归零**——闸门位置要放在 activity/斜坡归零调用之后、真正发包之前；同时留一个计数器 + 一行 INFO 日志，「不发」不等于「不管」。

主人的标准（原话：「这个卡住是预期内，不用惊慌」；追问后的补充是「**在目前这个积压的整合解决之前**」）——他不能接受两件事：把预期现象报成故障（告警疲劳），和把真故障当噪声滤掉。所以**阈值必须自带「当前处于哪个阶段」这个前置条件**。

落地四条：

1. **先定义阶段，再定义阈值**。示例（Hindsight 队列）：积压量 > 每轮上限 = 阶段 A（积压期：单槽被长任务占着、retain 排队变慢、探针要等，全属预期，只记不报）；积压量 ≤ 上限 = 阶段 B（再卡才是异常）。**阶段变量自己也要写进报告**，否则读到报告的人无法判断该不该关心。
2. **不要在 prompt 里写「大概看一眼」，要写死取数字段与判据**：字段名（如 `/stats` 的 `pending_consolidation`）、阶段分界值、「真卡死」的两条联合条件（同一条 op 长时间占着 **且** 近期 LLM 调用一条成功都没有）。判据含糊的定时任务会自己发挥，把正常波动报成故障。
3. **prompt 里显式列「这些属预期、不要告警」的豁免清单**，把容易误报的已知正常态逐条点名（无载荷父聚合器 `payload_null=N`、探针排队、刷新任务空转等）；同时把不适用于当前阶段的量（如 `pending` 总数）明确划出界外。
4. **交给定时任务的每条命令，自己先跑一次**：实测踩过——写进 prompt 的取数配方（用 SQL 数未整合条数）因为容器里没 `psql`、也没连接串 env，任务根本取不到数。**没亲手跑通的命令不得进 prompt**；取不到数时就让它如实写「取不到」，**而不是当成异常告警**。

配套一条红线：健康回看类任务默认设定为**只读**（不改配置、不重启容器、不 DELETE/retry 队列任务），并只有真异常才额外推送，正常时只投简短摘要。


飞牛的「多事件合并通知」规则会把宿主的 SSH 登录/断开也推给主人 —— **每跑一次 SSH 命令就多几条通知**。频繁 SSH 排查 = 往主人手机上刷屏；改用容器内 bind mount / 官方 trim-cli 通道（本就是本机既定的通道优先级），或把那条规则关掉。
