# 云端 LLM API 价目与成本口径（用前必重查）

价格频繁变动（DeepSeek 一个季度内两次调价并改峰谷结构），**任何数字都不能凭记忆用**：先 `web_search "<模型> 价格 每百万 tokens 高峰 空闲"`，以官方 pricing 页为准（价目表常在 JS 里抓不到，就用搜索摘要拼数字并注明来源）。二手博客的数字经常抄错。

## 计费结构与口径

- 输入分**缓存命中 / 未命中**两档，输出一档；部分厂商分峰谷（高峰时段 = 周一至周五 9:00-12:00、14:00-18:00 北京时间，其余空闲，空闲价常为高峰一半）
- **缓存命中基本不可能**（consolidation 每批输入都不同、prompt 前缀不重复）→ 估算一律按**未命中价**，别乐观
- 成本 = `tokens/1e6 × 单价`，输入与输出分开算

## 实测 token 口径（Hindsight 场景）

- 真实用量入口：`GET /v1/default/banks/<bank>/llm-requests`（拿 input/output tokens 取平均，别估算）
- consolidate 实测：每批 8 条 memory units ≈ 2540 in + 789 out tokens；119 批 ≈ 302K + 94K
- **两笔账不能混**：consolidate = 合并库中**已抽取词条**（~0.3M tokens，1-3 元量级）；全量重抽取 = 重读**原始文档**（~42M tokens，空闲 ~72 元 / 高峰 ~145 元）

## 何时值得切云端

- 本地模型干不了才干（例：consolidation 在 qwen3:8b 上 JSON 截断死循环）；日常 retain/recall 本地够用
- 云端是临时工具不是依赖；持续成本要算：新记忆每周积压 ~350 条 ≈ 0.3-0.6 元/周
- 预算敏感（本机 ~15 元/天）时先算这笔账，再决定走本地还是云端
