# delegate_task 分工工作流（主对话不卡顿）

主人 2026-09-07 定调：主对话只聊天+判断+派活；执行类任务一律 delegate_task 子代理。**子代理一次性、上下文纯净（只有任务书），跑完结果作为一条消息返回就结束**——没有持续会话就不会乒乓，OpenClaw 时代的禁言令/报告写文档/静默回执补丁全部退役。

## 何时必须派（判据）

- **预计 ≥3 轮工具调用的执行/排查/调研活，第一时间 delegate_task**，不许在主对话顺手连环调工具（SSH 查日志、批量 curl、多轮 grep 是典型）。
- 识别到「这活要挖」的瞬间就派，不是干到一半才想起——中途想起也要立刻转派，别硬扛完。
- **修复/改配置类同样算**（2026-09-16 补）："链路断了要修通"很容易被当成"顺手弄一下"，实际是排查+改配置+多轮验证。估轮数，≥3 就派。反例：修 fygo-browser CDP 链路在主对话跑了十几轮 SSH/curl。
- **先判要不要查（2026-09-16 主人定）**：主人只是陈述、确认、或自言自语式技术判断时，**能直接答就直接答，不要开调研**——宁可截断话题，也别把主干变成工作台。只有"这个结论必须准确、错了会害他"才去查，且照样派出去。原话：「如果没必要查我也好让你截断」。
- **上下文隔离本身就是派活理由**：已知会污染主上下文的活不要自己读——provider 内容风控敏感文本（代理/机场/订阅类全文、节点清单）、超长日志、整站抓取原文，一律交子代理读，只回收**脱敏结论**，并在任务书里要求它回报不复述敏感原词。主会话被污染是**自锁**的：命中片段钉在历史里、每次请求重发，此后怎么聊都撞（机制与三步定位见下节「派活的另一条硬理由」+ `references/provider-content-moderation.md`）。
- 反例（2026-09-07 血泪）：排查 H 库 retain 失败在主对话连环 SSH/curl/grep 半小时，主人「硬控半小时啥都干不了」。

## 派活的另一条硬理由：provider 内容风控会把主会话锁死

国内 provider（DeepSeek 等）可能返回 `HTTP 400: Content Exists Risk`。**审核在输入侧**：整条请求体（system prompt + 全部历史 + 工具返回）一起过风控，命中即拒、模型根本没运行 → 重试 / 换说法 / 降温度 / 调参数**全部无效**，别在这些方向上耗轮次。

- **污染是自锁的**：命中片段一旦进上下文就永久钉在历史里，此后每次请求原样重发，这条会话怎么聊都撞。所以**不要在被污染的主会话里 grep 那些原文**——读取本身就是把雷踩实；派子代理去读，任务书里写明它只回报文件位置与结论、**不复述敏感原词**。
- **成段全文远比零散词危险**（技能文档、配置清单、订阅节点表进上下文时命中概率高）→ 代理 / 网络这类高敏领域的原文一律由子代理处理，主会话只收脱敏结论。
- **「需要继续干活」不等于「需要主人开新会话」**：子代理和 cron 有自己的上下文，可直接承接后续任务；只有「这条主会话本身还要接着用」时才 `/new`，或切 provider（换家即绕开，与内容无关）。别一发现污染就要求主人开新会话——他会直接反问「你直接放子 agent 不行吗」。
- **`/new` 不是万灵药**：换会话只在「这次的读法变了」时有用。新会话里把同样的读取命令原样重跑一遍 = 把雷重新埋一次，于是变成「换会话 → 又撞 → 再换」的死循环（实测一个上午连撞 5 条会话，每条都在做同一件事）。要 `/new` 就同时改读法（走脚本过滤 / 派子代理）。
- **子代理自己也在这家 provider 上跑，它一样会被 400 拒**。所以高敏领域的任务书必须自带一节硬约束：不许 `cat`/`read_file` 整份配置、日志、订阅、节点清单；一切输出先过滤（`| grep -c`、`python -c` 只 print 布尔/码值/单行、`curl -o /dev/null -w '%{http_code}'`）；指代具体对象用它的 `md5` 前 6 位；已经撞过一次就换纯脚本式继续，**不许重试同一调用**。
- **高敏活怎么核验（脱敏句柄）**：任务书要求子代理把结论写成**只含布尔/计数/码值/哈希**的结果文件（如 `{"match": true, "proxy_http_code": "000", "exit_country": "SG"}` 那种形态），父级读这个文件、再自己跑一条端到端命令复核。「子代理自报不算证据」与「不许把原文拉回主上下文」这两条硬规矩靠它才不打架——核验走脱敏句柄，不走读原文。

三步定位（拿失败请求原文 → 按时间戳 diff 出「首次 400 前新进上下文的那几条」→ 另开一条全新会话做对照组证明话题词无辜）、已知高敏内容类型、以及给主人的结论口径见 `references/provider-content-moderation.md`。

## 子代理的工具面 = 父级工具面（先确认再派）

`tools/delegate_tool_toolsets.py`：**子代理永远拿不到父级没有的工具** —— 显式 `toolsets` 会与父级（复合展开后）的工具集求交，没写就**继承父级的 enabled_toolsets**，再剥掉 `DELEGATE_BLOCKED_TOOLS`（`delegate_task`/`clarify`/`memory`/`send_message`/`cronjob_manage`）以及 `delegation`/`kanban` 整套。

**后果（实测）**：某个 profile 被收窄过 `platform_toolsets`（如第二道门只留 `[memory, vision, delegation]`）之后，**它派出去的子代理只剩「看图」一个工具**——派活等于没派：子代理读不了文件、跑不了命令，只会把能力不足写成「查不到」交回来。

规矩：**派活前先确认当前会话/profile 的工具面里还有 terminal/file/web**（`GET /v1/toolsets` 或直接看可用工具清单）。被收窄过的 profile 上不要靠 delegation 兜底——要么把工具放回去，要么把活投给工具完整的那个门（主 profile／干活门）去做。

## 任务书怎么写（子代理对本对话一无所知）

必须自包含，包含：
1. **Goal**：一句话要达成的结果 + 验收标准（怎么算过/怎么算失败）
2. **Context**：环境（主机/路径/凭证获取方式而非明文）、现状、已排除项、关键背景——子代理没有本对话历史，所有需要知道的都写进去
3. **Steps**：按序给出具体命令/调用/决策点，每步怎么做
4. **已知坑**：把该领域 skill 里的坑精简进任务书（子代理看不到你已加载的 skill，除非你让它去读）
5. **汇报格式**：要求输出什么字段、用什么语言
6. **清理要求**：如果任务涉及临时文件/测试数据，明确要求清理（尤其别污染 Hindsight 记忆库——测试只许直连 ollama，不许走 retain）
7. **输出风格（省 token，主人 2026-09-12 定）**：纯执行类子代理要求全程 **caveman 风格**——去修饰词/客套/铺垫，短句、碎片句均可；技术术语、路径、代码、报错原文照抄。理由：子代理全程跑工具调用、每轮重发上下文，压缩输出是白捡的省耗。做法：直接把这套要求写进任务书（或让其读 skill `caveman`），不必改配置。

8. **工具自修要求（主人 2026-09-13 定）**：任务书里必须写明——搜索/抓取工具不通时**自己动手修通，不许轻易记为「未找到」**。可用手段：换搜索入口（360/搜狗/Bing/DDG）、curl 走代理、直连目标官网、微信公众号正文（iPhone MicroMessenger UA）、GitHub raw、镜像站、换 UA、加延时重试、自己写脚本抓。**禁止重复同一个调用**（会触发 `loop_web_search_cap` 被系统拦下、零产出），**允许不断换方法**；只有可行手段都试过仍拿不到，才写「未找到公开数据」并列出试过的路。

9. **不许动清单（收尾误杀教训）**：任务涉及宿主/容器进程时，任务书里必须**点名列出绝对不许杀、不许重启的进程与服务**（自己搭的常驻代理、Hermes 自身、正在跑的服务）。子代理清临时进程时是按**模式**杀的，会连带把你搭的常驻进程一起带走——实测它为了修一个应用，把宿主上我搭的 CDP 转发代理一起杀了，整条链路静默断掉，要等下次宿主重启才被 crontab 拉回；而它自己完全不知道弄坏了东西。

引用宿主环境时给 SSH 命令模板：`SSH_ASKPASS=/opt/data/scripts/askpass.sh SSH_ASKPASS_REQUIRE=force ssh -o ConnectTimeout=8 -o StrictHostKeyChecking=no 棉棉@172.17.0.1 "<cmd>"`；sudo 用 `SUDO_ASKPASS=/tmp/askpass_tmp.sh sudo -A`。

## 怎么拆：按轴并行 + 强制结构化输出

- **排查/查证类活按轴拆两个并行子代理**，比一个子代理串着干快且干净：①**本机探针**——在真机上跑命令、取真实报错与退出码、摸权限/配置边界；②**外部查证**——上网查这个报错码/这个权限模型的已知含义与解法。两轴互不阻塞，都装在一个 `tasks` 数组里派。
- **用 `output_schema` 逼出结论**：把你要拿来判断的字段写死（如 errno 含义 / 根因 / 能不能修 / 修不了时的边界清单），并在任务书里要求「数字与结论必须来自真实运行，搜不到就写找不到，不许编」。结果回来能直接采信，而不是又一篇流水账。
- **调研类再分两轴：生态实现 + 一手源码**（比「本机探针 + 外部查证」更适合「这东西该怎么做」类问题）：一轴查**别人怎么做的**（开源实现里的源码文件 + 函数名 + 函数行为），一轴查**上游自己怎么实现的**（协议端/官方仓库源码、schema、枚举定义）。生态实现常靠穷举与猜测（按关键词、扩展名、启发式），一手源码给的是**字段级判据**——两轴对上才敢写进方案。做法：`output_schema` 里加一个 `依据: [str]`（填 `文件:行` 或 URL）并要求**每条结论都填**，没有依据的它自己会写「找不到」，父级一眼分出哪些能采信；任务书里同时要求标注**源码快照的版本/commit**，并明说「上游源码与你本机跑的版本可能不一致，别把上游当本机事实」。
- **任务书里写清「只做只读探测」**：诊断类子代理容易“顺手修复”，把「不要改权限/不要重启服务/不要删东西」写在硬性要求里，只渎性质的例外单独点名。

## 任务切分与文件边界（并行施工的硬约束）

- **文件边界要逐份点名**（同日踩过）：两个并行子代理同时改同一个脚本（`health_all.py`）与**同一份人格文件**时，互相覆盖、一方刚做的改动被另一方顶掉，两边都以为自己做完了。任务书里的写法：「**你只准改 A、B 两个文件；其余文件一律只读**」，且并行任务的**可写文件集必须两两不相交**。
- **改同一份共享产物（人格库、config、在线服务）时宁串行不并行**（见下节并发边界）。
- **长任务切小，主任务优先**：主人原话——「可以顺手做别的，但是我的要求肯定要先完成」。任务书禁写「顺便把别的也改改」；顺手项单列、排在主任务验收之后，或干脆另起一个子代理。
- 长任务被中途打断（余额/额度/超时）时的捞回配方与「阶段成果先落盘」见下面「子代理中途死掉」两条——**续做前先读它的 live transcript**（`grep`/`tail` 取关键段，别整篇读）。

## 成本纪律（余额是单点；并行 = 成本乘 N）

主人踩过两次余额耗尽后的原话是「多路并行还是用的太快了」——**并行 N 个子代理不是 N 倍效率，是 N 倍成本**：每个子代理都带着自己那份长上下文，且**每轮全量重发**。规矩：

- **同时只跑一个**：除纯只读的短探针外，一律做完一个再派下一个；真要并行也只并**两轴**（本机探针 + 外部查证），不要同时开三四个写文件的活。
- **任务书的长度本身就是成本**：任务书越肥，子代理每轮重发的上下文越大。写短——目标 + 验收 + 已核事实 + 硬约束；长背景改成「先读 <文件> 第 N 节」，不要整段抄进来。
- **机械活先落成脚本，别派 agent**：能写成幂等脚本、跑一条命令看退出码的活（体检、核对配置值、md5 对比、批量改一处参数），走脚本 + `no_agent` cron = **零 token**；只有真需要判断/多轮试错/改代码的才派子代理。
- **一条命令能办的不派**：改一个配置键、重启一道门、回读一个字段，父级自己做完更便宜，别为它写一份任务书。
- **余额/额度断了先「捞」不要重跑**：402 之类中断后产物常常已经落盘（实测一份 1059 行的文档在被 402 掐断前正文已写完，丢的只是它的汇报）→ 先核目标文件/服务状态，再只补差的那几步（配方见上文「从记录里捞回来」）。

## 派后管理

- dispatch 后主对话立即恢复，正常聊天。子代理完成时结果自己冒出来，**不要轮询**（delegate_task action=list 只在用户问进度时用）。
- 中途纠偏用 `delegate_task(action='steer', subagent_id, message)`——排队插到它下个工具结果后；子代理快完成时 steer 可能赶不上，会被报为 missed_steer，属正常。
- 子代理结果返回 = 处理链：读→判断→（需要则）报主人→结束，无需回执。
- **零产出不要原样重派（2026-09-13 实测）**：子代理若因工具死循环（如 web_search 被 cap 拦下）零产出，重派时把失败原因写进新任务书的「工具策略」段——明确禁止重复同一调用、给出已验证的替代入口（实测可用：`HTTPS_PROXY=http://172.17.0.1:17890 curl -s -m 25 -A "Mozilla/5.0 ..."` 抓 `https://www.so.com/s?q=`，PC 版结果 `data-mdurl` 属性即真实 URL；百度会触发验证码；CDP 浏览器不通）。
- **子代理中途死掉（报错/账单/超时）≠ 什么都没做（实测）**：它可能已经完成了关键步骤（实测：子代理被 402 账单错误打断前，已把目标应用从 blocked 状态救回来），也可能顺手弄坏了别的（同一次它杀掉了常驻代理）。收到 failed / 中断回执后**必须自己复核目标系统状态**（关键进程在不在、端口通不通、文件落没落），再决定补做还是重派：不要因为它「没跑完」就从头再来，也别因为它说 completed 就免检。
- **中断的活要「从记录里捞回来」，不是重跑**（可复用配方）：每个子代理都在 `/opt/data/cache/delegation/live/<delegation_id>/task-0.log` 留**逐条过程记录**（工具调用 + 结果摘要），中断时最后的成交通常已落盘。做法：① `tail -25` + `grep` 看它最后在做什么、哪些步骤已完成；② `find <产出目录> -newermt '-40 minutes' -type f` 盘一遍**它到底造了哪些文件**（比读日志快）；③ 跑一次该环境的健康自检确认**没被留在半路**；④ 重派时把这三样写进新任务书，并明确要求**先读那份记录、不重做已完成部分**（省 token），只做「差的那几步」。
- **长活要分段交付，别指望一次跑完**：子代理跑得越久，中途撞上账单/额度/上下文上限的概率越高（实测一次 14 分钟、136 次调用的任务被 402 掐断，最终报告丢失）。对策：任务书里要求**阶段成果先落盘**（文件/提交/配置生效即算，报告可以后补），并把「余额/额度是不是够」当成跑长活前的检查项——余额是单点，断了所有子代理一起哑。
- **子代理结果是自报，不是已验证事实**：外部副作用（上传/写文件/API 调用）需可验证句柄（URL/绝对路径），验证后才向主人报成功。
- **要等几分钟才有结论的验证，派子代理去盯，父级不许干等**（主人原话：「盯着看你自己真盯着干嘛，派个子agent得了」）：容器稳定性观察、构建、批处理、限时探针这类活，别在主流程 `sleep` 轮询，也别把父级的回合耗在上面——派一个盯梢子代理，或挂成后台任务。判据：预计等待 > 1 分钟就派。
- **给盯梢子代理预授权一个「条件动作」**：任务书里把**唯一允许它动手的触发条件**写死（如「只有 API 不通 + `RestartCount≥2` + 日志出现 startup failed 三条同时成立，才执行已经准备好的回滚脚本；其余任何情况都不许改配置、不许重启容器」）。这样你在不看着的时候它也能兜住真崩，又不会自己乱动。回滚脚本**提前备好、路径写进任务书**，不要让它在现场现编。
- **主动停掉 / 被中断的子代理没有总结，它没交的判定要自己补验**：回执可能是 `status=interrupted` + `(no summary)`，你以为的「它会告诉我结果」不会发生——用 `action='list'` 看它是否还在跑，掐掉之后自己把该验的验一遍再下结论。另外回执会点名**它留下的后台进程（已随它一起被终止）**：那些进程是真死了，需要就重开，别当它还在后台跑。
- **子代理改过的文件要核「属性」再核「能跑」**：光看它自报「已改好、已验证」不够——实测它把脚本的可执行位弄丢（644），挂上 cron 的脚本直接不跑。父级必须 `stat -c '%a'` 看权限位（该 +x 的补回来），再**把那个产物自己执行一遍**（不是读它，是跑它），才算验完。
- **「元数据类结论」要回主源验，别信转述**：星标数、许可证、文件大小、仓库真实性这类结论，子代理很容易只看了 README 徐章就下结论。做法：**自己拉 LICENSE / 元数据原文核一遍**（实测子代理报「MIT」而 LICENSE 文件首行是 `GNU GENERAL PUBLIC LICENSE Version 3`）。许可证直接决定能不能拄代码，不能靠转述。
  - 具体通道：**GitHub 匿名 API 额度（60/h）很容易被调研类子代理一次打完**（回报 `rate limit exceeded`）——此时改用 `https://raw.githubusercontent.com/<owner>/<repo>/<main|master>/LICENSE` 直接取文件，**不占 API 额度**；仓库元数据再用 web 搜索交叉。额度打满时如实说哪些数据没取到，**不要把子代理转述的星标数当自己验过的写进结论**。
- **诊断类结论也要自己复现一次再采信**：子代理给的「根因是 X / 这个功能可用 / 是权限问题」都是**待验证假设**，不是结论。主对话拿到后跑一条端到端命令复核再往报告里写（实测踩过：本机探针子代理把某个自定义 errno 判成「权限不足」，自己复现后才发现是会话过期；另一轴的上网调研也照着错误推断给了建议）。**回读类判据（API 状态回读、配置回读、文件已写入、hash 匹配）只证明「动作生效」，不证明「目标达成」**——切个开关回读一致、端到端依旧不通是常态，报「成了」之前那条真实链路的返回码必须到手。
- **两轴结论冲突时，本机实测 > 网上推断**：外部查证轴回答「一般情况」，本机探针轴回答「这台机器」；两者不一致就按实测写结论，并在报告里说明推断为何不成立。

## 多个子代理同时施工同一个在线服务（并发边界）

当一个活要拆成几个子代理、而它们都要动**同一个正在跑的服务**（本机典型：AstrBot 聊天门——插件、配置、重启都只有一份）时，任务书里必须先把并发边界写死，否则两边互相覆盖、重启打架：

1. **逐份点名「不许碰什么」**：不碰兄弟任务的目录/文件，不改对方的开关。
2. **重启前先看服务是不是正在启动中**（日志末行 / 容器 `State.StartedAt`），错开时间再操作。
3. **重启后照一份固定清单逐项核**，且清单必须包含**各插件的配置值**——不只「加载成功没有」。兄弟子代理会把你的参数覆盖回旧值（实测：刚把某个插件参数从 7 改成 10，另一个子代理一重启就可能带回去）。这份清单要**原文写进每一份任务书**，并要求它回报逐项结果。
4. **同一台服务上宁串行不并行**：能排先后就排先后；非并行不可时至少保证「同一时刻只有一个改它的写入者」。

## 子代理停在「还差一步」时，父级接手

子代理会保守地把「需要重启线上服务 / 超出它自己判断的安全线」的步骤标成**未做**并交回来（实测：插件代码已部署到盘上，但因为「线上通道是红线」没重启 → 实际跑的还是旧版）。父级的动作：
- 先判这一步是否在**自己**的授权范围内（主人已点头的、可逆的），在就直接执行，**不要把它退回给主人当待办**；
- 执行后照样按复核清单验一遍（md5 / 就绪日志 / 健康行），再向主人报「已上线 + 判据」；
- 反之若确实是主人才能拍的板（重建容器、改他人数据），才回给主人，并写清「差的就是这一步」。

## 主人中途改方向：steer 改派，不要 stop + 重派

同一个子代理还在跑时收到新指令/用户改了主意，用 `action='steer'` 把新口径压给它：
- 它已经跑出的只读成果（源码行号、可用路径、已验证的接口）能被新一轮直接复用；stop + 重派等于把已花的 token 丢掉。
- 新决定（如「A 关掉、只做 B」「②别做了」）可以直接让**那个正跑着的子代理**去执行，从而避免父级和子代理同时改同一台服务（也避免两个写入者抢重启）。
- steer 后留一手：它若在中途完成、赶不上这条 steer，会以 `missed_steer` 报回——那就按新口径自己补做或再派一轮小任务，别当没说过。

## 汇报给主人：给判断，不贴记录

主人明确表达过「重新解释一下，我不想看记录」——把日志原文、测试输出、逐项证据表格堆给他，等于没汇报。规矩：

- **先给判断**（能一句话选就一句话），理由压到 2–4 条；**日志与命令只是我自己的判据**，要留痕就给他路径让他自己翻，不贴正文。
- 需要他拍板时给**候选路线对比 + 我的推荐 + 一个明确的选择题**（「回一个字就行：A 还是 E」）——他会直接回选项，这样一轮就能定。
- **后台任务的完成通知本身就是发给主人的一条消息**（`terminal(background=True, notify=True)` 每跑完一条推一条）——连跑 6 轮全量回归，他看到的就是 6 条重复回执（原话：「怎么这么多重复回执」）。所以验证要捐着跑：**小测走前台**（秒回、不推送），**全量回归只在收尾跑一次**，改到一半不跑全量；中间态不逐条回报，一轮改动只回一条结论。通知真重了，一句话说明它对应哪次跑就行，别把上一次的结论重讲一遍。
- **他人在外面/手机上（路上、军训间隙）时更短**：结论 + 要他做的一件事，其余留到他坐定。
- 但**证据链不能省在自己身上**：向他汇报前该跑的复核（md5 双向、真轮日志、生产函数实跑）照跑，只是不贴给他看。

## 跨门 A2A 派活：调用方会被挂住到对端回合结束

`delegate_task` 是异步的（派完就回），**跨门 A2A 不是**——这个区别坑过一次大的。

**机制**：`a2a_call` 发的是一个**阻塞的 HTTP POST**；对端把它丢给本地 gateway 后
**挂住响应，直到那个 agent 回合跑完**。所以：

- **对端在回合中间说的任何话，调用方一个字都收不到。** 「先喊一声『已接单』再接着干」
  在这条链路上**物理上做不到**——Hermes 一个回合只产出一条最终消息。
- 调用方被挂住的时长 = `a2a_agents.<agent>.timeout`。诊断看**对端**的
  `logs/gateway.log`：`response ready: platform=a2a … time=<秒>`——那是真实回合时长，
  见到几百上千秒就说明有人把长活在回合里干完了。
- ⚠️ **推送回调不是解药**：`configuration.taskPushNotificationConfig`（HMAC 签名）
  注册后服务端**照样挂住响应**，推送只是「额外抄送一份」，不能让调用方脱身。
- 判据（自己复现一次再下结论）：`a2a_call` 发一条无害消息，看对端日志里的 `time=`。

**正确做法 = 让长活不占回合**（而不是在回合里「先回一句」）：
1. 对端收到就把长活**甩出回合**（后台终端 / 定时任务 / 异步派发），本回合**尽快结束**；
2. 真正的活在回合外跑，产物写到任务书 `Deliverable` 约定的路径；
3. 跑完由对端**主动推回**（见下）——长活不回报 = 派活方只能再派一趟问。

## 与独立 worker 的取舍

- delegate_task 子代理：零部署、上下文纯净、跑完即焚——日常排障/批处理/调研首选。
- 独立 profile worker（hermes peer）：只有要「长驻执行体」（跨天自愈巡检、自己积累经验主动找活）才值得，代价是维护第二套人格/记忆/skills/凭证。
