# 交付物自审

主人说「你自己看看有没有什么可以改进的」「你自己把握就成」= **授权自主动作**：
不必逐项请示，也不该先问要不要做。红线照旧——不可逆操作、删除、动他人的东西仍要问
（删文件走回收站/备份目录，不用 `rm`）。

产出不是「我检查过了」，而是**找到并修掉的缺陷 + 可复现的证据**。
只报告「看着没问题」等于没做。

## 步骤

1. **把文档里声称的能力逐条实跑**
   列出 README / docstring / `--help` 承诺的每个能力（输入格式、可选开关、回退路径），
   各跑一次。文档说支持但从未测过的，几乎总能捞出真 bug；「文档说支持但没测过」
   比「文档没写」更糟——使用者会信它。
2. **给每条 headline 结论补量化支撑**
   结论里的形容词（「更准」「更快」「够用」）各配一个可复现的数字
   （准确率、耗时、峰值内存），一起写进文档。缺数字的结论留不住。
3. **验收指标要选对，别被顺序差异骗了**
   比较生成结果与预期时，顺序敏感指标（逐字 diff、LCS）会把「内容全对但顺序不同」
   报成「大量错误」。用顺序不敏感的指标（字符集合覆盖率）量内容，
   顺序单独核验，两项分开看。
4. **找静默失败模式，按风险不对称定默认值**
   优先找「不报错但丢内容」的路径。默认值必须偏向不丢：有损或省资源的开关默认**开**
   （保留完整能力），用 `--no-x` 显式关；只省一点时间却有丢内容风险的开关，绝不设为默认。
   例：「有电子页眉的扫描页」若只按文字层字数判为电子页，会静默丢掉整页扫描正文。
5. **检查同一交付里有没有互相矛盾的多份文档**
   长期调研常留下中期报告 + 最终 README。两份给相反建议 = 使用者不知道该信哪份。
   收尾时扫一遍同目录文档：保留双方的有效实测数据，把结论统一成「按条件二选一」的判据，
   并在被取代的那份顶部标注已被取代（**别删对方的数据**）。
6. **修复必须配回归，且要有「新旧逻辑判定不同」的构造用例**
   写一个覆盖各路径的回归脚本（每条路径一行结果），跑完把结果贴进文档。
   对逻辑修复要构造能把旧、新逻辑分开的样本——判定条件得落在模糊区间里；
   边界外的样本两种逻辑同结果，证明不了修复生效。
   三条补充：
   * **钉子写完后把修复临时拿掉跑一次，确认它变红**。不红的钉子是包装，不是防线；
     变绿只能证明「代码现在这样」，证明不了「它在防这件事」。
   * **每种输入形态各一条用例，特别是短路写法后面的分支**：`x = x or f()` 这类写法会让
     后半个表达式在部分分支上**永不执行**——那条分支的业务代码一次都没跑过，用例还全绿，
     只有真实输入形态（另一种会话类型、缺字段、命中兜底）才会踩到它。
   * **静默失败要额外取证**：异常被 `except` 吞成一行 WARNING 的路径，返回值看起来「跑过了」。
     验收这类改动不能只看返回，要看日志里有没有那一行失败（或计数/状态文件有没有推进）。
7. **顺手收尾**：停掉测试起的常驻进程、报告回收了多少内存、
   把被否掉的方案占的磁盘列成可选清理清单（给出命令，别替主人删）。
8. **把发现写进交付文档**，不要只在对话里说：加一节「自审修复记录」，
   用「问题 / 后果 / 状态」三列表 + 回归结果表。

## 坑

- **别把「改得多」当「改得好」**：默认值反转、重复开关、无证据的措辞润色都不算改进。
  每条改动要能说清后果是什么。
- **改入口脚本前先停掉在跑的长任务**：新旧代码混跑的测试结果不可信，跑完还得重来。
- **`pkill -f <模式>` 会匹配到自己的命令行**：模式含正在执行的脚本名时会把这条命令自己
  杀掉（表现为莫名的 SIGTERM）。用 `pkill -f "[m]ineru-api"` 这类方括号技巧，或按 PID 杀。
- **别每改一处就起一轮全量回归后台任务**：后台任务完成会折一条回执给主人，改五轮就是五条
  「已完成」（主人会问「怎么这么多重复回执」）。定点测试/小脚本走**前台**（快、无声），
  全量回归在**收尾跑一次**；中间态失败自己看日志消化，不逐条汇报。
- **同一脚本里批改多个文件时，每个文件用独立变量名**（`a_text` / `b_text`），不要共用一个变量再写盘：
  混用会把 A 的内容写进 B（实测把协议层源文件整个盖成适配器代码，当场几十个用例全红）。
  写盘前 `assert 命中次数 == 1`，写盘后立刻 `ast.parse` 再报「改好了」。
- **长任务别接 `| tail -N`**：中途看不到任何输出，只能干等结束。改成 `> 日志 2>&1`
  再分段读日志；后台任务用 notify 等完成通知，别反复轮询阻塞对话。
- **同源两套接口的返回结构常不一致**（HTTP 服务 vs 命令行、不同版本之间）：字段一个是
   list 一个是 JSON 字符串、`page_idx` 一个是 int 一个是 `'0'`，照惯用写法解析会
  崩或静默输出空。跨通道复用的解析代码，两边都归一化并在两条路上各测一次。

## 汇报给主人时

只列**改动了什么 + 证据**，不逐条复述过程（主人偏好：只列要动的，其余一句带过）。
修掉的问题按「后果」排序，最严重的在前；收尾状态用一条短句带过（进程停了、内存回收多少）。
